# SCOS 关键业务流程 SVG 绘制规范与验收清单

## 1. 文档目的与适用范围

本规范用于统一 SCOS 业务蓝图中关键业务流程图的业务表达、视觉样式、SVG 实现和交付验收。适用于库存、采购、计划、成本、驾驶舱等模块。

样式基准依次为：用户最新确认的流程图截图、《SCOS蓝图（样式-全）》在 WPS 中的流程图显示效果，以及项目现有《SVG流程图绘制规范与验收清单》。发生差异时，以最新明确确认的样式为准。

## 2. 核心原则

1. 不因排版改变业务节点、角色、顺序、分支或业务口径。
2. 一张图只有一个开始和一个结束，所有终止路径进入同一结束节点。
3. 泳道名称必须在左侧，泳道按参与角色或系统从上到下排列。
4. 所有背景保持白色，不使用泳道底色、渐变、阴影或纹理。
5. 连接线不穿过节点、文字、标签或其他连接线；每个实际入口都有独立箭头。
6. 图内信息以业务动作和责任为主，不展示公式、程序组件或算法推导。

## 3. 画布与外框

- 使用白色画布；宽高按流程复杂度扩展，禁止为固定尺寸压缩节点和文字。
- 顶部设置完整标题框，内容为“流程编号及名称：（流程编号 流程名称）”。
- 标题框与下方泳道主体左右边界对齐，底边与主体顶边连续。
- 外框、泳道分隔线和节点边框采用 `#808080` 或视觉等效细灰线，建议 1—1.2px。
- 主流程线采用黑色实线，建议 1.5—2px。
- 不增加顶部泳道标题行，不使用浅蓝或灰色泳道背景。

## 4. 泳道

- 泳道是上下排列的水平区域；左侧设置统一宽度的泳道名称列。
- 泳道名称逐字符纵向排列，中文、英文和斜杠均各占一行。
- 名称列按最长角色从紧设置，以完整容纳文字并保留 10—16px 安全边距为准。
- 泳道名称水平、垂直居中，不压线、不越界。
- 同一执行主体的节点必须落在对应泳道内；跨角色处理应拆分为不同节点。
- 当只有一个角色时仍保留左侧泳道名称列，样式与模板示例一致。

## 5. 字体与颜色

| 用途 | 字体 | 建议字号 | 样式 |
|---|---|---:|---|
| 流程标题 | SimSun、Songti SC、STSong、serif | 20—23px | 黑色、600 |
| 泳道名称 | SimSun、Songti SC、STSong、serif | 15—18px | 黑色、常规 |
| 节点编号 | SimSun、Songti SC、STSong、serif | 13—15px | 深灰、常规 |
| 节点名称 | SimSun、Songti SC、STSong、serif | 15—17px | 黑色、常规 |
| 分支说明 | SimSun、Songti SC、STSong、serif | 13—15px | 深灰、常规 |
| 业务口径 | SimSun、Songti SC、STSong、serif | 13—14px | 深灰、常规 |
| 系统标签 | Arial、Microsoft YaHei、sans-serif | 12—14px | 白色、常规 |

系统标签固定颜色：SCOS 为蓝色 `#008ACB`；数据服务或外部系统为绿色 `#00A651`；线下人工活动为紫色 `#7030A0`。不得增加无定义颜色。

## 6. 节点

- 开始、结束：白底灰边圆形或椭圆形。
- 业务处理：白底灰边矩形。
- 判断：白底灰边菱形，所有分支出口完整。
- 单据或数据输出：白底灰边文档形；只表达关键输入输出，不作为新增流程步骤。
- 同类节点的宽、高、边框和文字位置保持一致。
- 节点编号在节点内单独一行，业务动作位于编号下方。
- 系统标签放在节点左上角并与边框轻微重叠，标签不得遮挡编号或动作文字。

## 7. 布局

- 主流程优先从左向右展开；同一角色连续动作可在本泳道中水平排列。
- 跨泳道时使用水平—垂直—水平的正交折线进入目标节点。
- 节点之间保留足够空间容纳箭头、Y/N 和业务条件文字。
- 判断分支应在出口后立即拉开，返回路径放在主流程上方、下方或画布外侧的保留通道。
- 若空间不足，优先扩展画布，其次调整节点位置和文字换行，不缩小全部节点。

## 8. 连线和箭头

- 所有流程线使用黑色实线、直角折线和统一实心箭头。
- 线条从源节点边界发出，箭头尖端准确落在目标节点边界。
- 每个进入节点的路径必须是独立 SVG `path` 并单独使用 `marker-end`；禁止一个 path 包含多个 `M` 子路径。
- 多分支汇流时，各支路先使用无箭头线段到汇流点，再用一条带箭头的共享线进入节点。
- 不同流程线不得交叉；相同路径不得重复绘制双线或双箭头。
- 连线不得穿过节点、系统标签、文字、泳道名称列或业务口径。

## 9. 判断、分支和返回线

- 判断文字写成可回答的是非问题或明确条件。
- Y/N 或完整条件放在对应出口附近，并与实际线路方向一致。
- 业务条件较长时放在线路旁，不压在连线上。
- 返回线选择最短且可辨认的路径，进入原节点时必须有箭头。
- 多条返回线进入同一节点时，可在目标附近汇流，但来源必须清晰。
- 所有“无需调整”“不纳入”“审批不通过”等终止分支必须明确进入下一业务动作或唯一结束节点。

## 10. 子数据节点和输出物

- 子数据节点宽、高均小于父业务节点，位于父节点右上方并少量重叠。
- 父子之间不画连接线；父节点主流程线绕开子数据节点。
- 子数据节点保持白底、灰边和与正文一致的字号，不使用大面积色块。
- 无助于业务人员理解的中间数据不绘制。

## 11. 底部业务口径

- 使用“业务口径：……”单行或自然换行文本。
- 位于泳道主体外框以内的左下角，从泳道名称列右侧开始。
- 不增加底色、文本框或额外分隔区。
- 与最下方回线、结束节点和外框保持清晰间距。

## 12. SVG 实现要求

- 样式集中定义，至少包含 title、lane-text、node-text、small-text、note-text、node、divider、flow、flow-stem、tag-scos、tag-external、tag-offline 和 tag-text。
- 箭头使用统一 marker；调整 `refX` 使箭头尖端位于节点边界。
- 每个带箭头 path 只包含一个 `M` 起点。
- 绘制顺序为外框与泳道、连接线、节点、系统标签、文字、分支说明、业务口径；必要时确保标签覆盖节点边框但不遮挡连线。
- SVG 必须设置 `viewBox`，使用字体回退栈，不引用网络字体或外部资源。

## 13. 文件和版本

- 原始 SVG 保留；优化版采用 `_优化.svg` 后缀，除非用户明确要求直接更新现有优化版。
- 正式资产目录只保留 SVG 原文件和文档实际引用的图片；临时预览放入临时目录。
- SVG 文件名、文档图题和流程名称必须一致。

## 14. 验证方法

1. 使用 `xmllint --noout` 检查 XML。
2. 统计带箭头 path，确认不存在复合多 `M` 路径。
3. 使用 Quick Look 或受控渲染器生成高分辨率 PNG。
4. 先检查全图，再局部放大所有判断、回线、汇流、结束节点和左侧泳道名称。
5. 嵌入 DOCX 后在 WPS 中按适合页宽查看，确认文字可辨、比例正确且未被裁切。

## 15. 交付前验收清单

### 15.1 画布与泳道

- [ ] 白色背景，无泳道填色、渐变和阴影。
- [ ] 标题框四边完整并与主体外框对齐。
- [ ] 泳道名称全部位于左侧且纵向排列。
- [ ] 泳道名称未越界、未压线，名称列无明显多余空白。

### 15.2 节点与文字

- [ ] 开始和结束各一个。
- [ ] 节点位于正确泳道，同类节点尺寸一致。
- [ ] 编号与名称分行，文字无溢出或裁切。
- [ ] 系统标签颜色、位置和字号统一。
- [ ] 子数据节点小于父节点且父子之间没有连线。

### 15.3 连线与分支

- [ ] 每个真实入口均有完整箭头。
- [ ] 箭头尖端落在节点边界，未进入节点内部。
- [ ] 不存在复合多 `M` 箭头路径、双线或双箭头。
- [ ] 连线之间、连线与节点之间无交叉和非必要重叠。
- [ ] Y/N 与线路方向一致，长条件文字未压线。
- [ ] 返回线和汇流路径清晰，所有终止分支进入唯一结束节点。

### 15.4 业务与文件

- [ ] 图中节点、角色、分支与节点说明表完全一致。
- [ ] 业务口径位于泳道主体左下角且未被遮挡。
- [ ] SVG 通过 XML、渲染和局部视觉检查。
- [ ] SVG 原文件与文档嵌入图片均已保留并正确命名。
