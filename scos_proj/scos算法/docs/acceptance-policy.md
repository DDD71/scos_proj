# 分批验收与交付规则

六个业务包分别签收，包内各项单独留证。驾驶舱中的沙盘单独列项；跨包联动验收单列，不把后续包未完成作为阻止先行包离线计算验收的理由。尚未实现能力保持“未实现/未验收”，不将目录、构建成功或 Demo 展示作为验收通过。

## 每批固定内容

每批验收记录必须包含：包名和版本、业务蓝图场景及规则条目、纳入/排除项、源代码提交、契约版本、模型版本、参数、固定数据集及摘要、运行环境、锁定版本的 POM 和解析后的依赖清单、预期结果及容差、实际结果、耗时、报告、缺陷及业务签收人。版本发布后不覆盖原制品；未通过项与批准延期项分开记录。

最终交付物包括源码、独立 JAR/POM、源码交付物、需要部署时的 Java 服务镜像及摘要、输入输出契约、模型/规则说明、部署说明、离线算例、预期输出和测试/验收报告。当前骨架的构建文件尚未包含运行依赖；正式交付时每包锁定自身依赖，不依赖开发人员本地环境。

## 验收分层

1. **契约评审**：确定输入粒度、单位、精度、时区、必填/缺失语义、输出、状态、错误码及模型版本兼容；每包自行维护 Schema，不共用无约束的任意 JSON 代替定义。
2. **离线计算验收**：只需要 JDK 和本包已解析的依赖，不需要 Spring Boot 业务后端、浏览器、其他包服务或生产数据库，使用已确认输入和参考输出检验正常、边界和异常；优化类检查硬约束、可行性、目标值/差距，计算类检查守恒与精度，分析/追溯类检查范围、路径及可解释性。
3. **服务集成验收**：检查 Java 调用、权限、版本、异步任务、幂等、超时、取消、重启恢复、重复/迟到结果处理和归档。此层未通过时不能宣称业务功能已上线。
4. **跨包业务验收**：用已发布包版本及同一快照验证沙盘、预警、成本/质量影响链路；其他能力缺失时明确未评估，不以模拟输出宣称集成通过。

算法回归数据可先使用脱敏样本，验收基准由业务人员确认，不能把算法自身输出无审核地复制为“正确答案”。不预设未经确认的节约率、准确率、性能或误差阈值；已有蓝图指标需要连同数据规模、硬件条件和测量方式登记到各包验收记录。

## 独立发布约束

- 六包各有 `pom.xml` 和版本，允许分别构建和发布。CI 后续按变更路径选择包，契约变更同时触发消费者兼容检查。
- 包内子算法通过验收项编号区分，不因内部每个函数新增一个分发包。
- 已验收包升级必须执行自身回归及受影响契约回归，破坏性协议变更提供新的契约主版本及迁移方案。
- 平台服务和算法包不得共享可变数据库表或隐式内存状态。跨包依赖通过显式数据契约与 Java 编排管理。
