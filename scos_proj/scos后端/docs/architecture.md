# 后端架构

## 架构选择

前后端分离，后端先采用模块化单体：一个 Spring Boot 进程、一个部署产物，按业务域明确数据和调用边界。算法核心采用独立 Java 17 / Maven JAR，服务适配层采用 Java / Spring Boot，可在独立进程中通过版本化 HTTP 接口接入。当前不引入微服务注册中心、Kubernetes、消息队列或 Redis 作为启动前提。

这种结构适合先落地跨模块计划、审批、版本和审计流程。模块独立不等于可以立即拆成服务；将来需要单独部署时，仍需重新处理身份传递、事务、失败重试和数据归属。

## 业务模块及数据归属

| 模块 | 职责 | 主要拥有的数据（计划） |
| --- | --- | --- |
| dashboard | 驾驶舱指标、预警、汇总查询 | 读模型、指标定义；通过模块契约读取业务结果 |
| sandbox | 情景配置、跨模块推演编排、方案比较 | 情景版本、推演步骤、比较结果 |
| inventory | 成品库存策略和优化 | 库存方案、参数、约束、结果版本 |
| procurement | 采购分析、优化及执行反馈 | 采购建议、供应商评价、方案与反馈引用 |
| requisition | 原辅包要货、日度计划和滚动调整 | 要货方案、调整记录、执行差异 |
| costing | 成本核算、差异分析和敏感性分析 | 成本模型、核算批次、结果明细 |
| traceability | 全程正反向追溯、质量影响分析及处置建议 | 追溯查询快照、关系引用、影响分析结果 |

`system` 前端菜单映射至 `platform` 能力，并不要求后端有一个巨大的 system 模块；`integrations` 菜单通过授权的查询/操作 API 使用外部数据，不直接访问外部系统。

SCOS 管理分析、决策方案和受控的执行建议。正式订单仍由 SAP/E采等业务系统负责。生产计划、排产、生产实绩来自外部 MES/计划系统，不新增排产优化模块；没有对应计算能力的情景标记为“未评估”。主数据与采集由数据平台负责，SCOS 保存决策所需快照和引用。

## 域内分层

每个 `modules/<业务域>/` 已预留以下目录：

| 层 | 放什么 | 依赖规则 |
| --- | --- | --- |
| api | Controller、输入校验、请求/响应 DTO、映射 | 调用 application，不直接访问数据库或算法 |
| application | 用例、事务边界、编排、端口接口 | 调用本域 domain、端口和其他域公开 contracts |
| domain | 聚合、值对象、规则、状态机 | 保持纯 Java，不依赖 Web、数据库或外部 SDK |
| infrastructure | Repository 实现、数据映射、端口适配器 | 实现 application/domain 端口，对接技术设施 |
| contracts | 对外公开的查询接口、命令和事件 DTO | 稳定且最小，不暴露持久化实体或域内实现 |

调用方向是 `api → application → domain`，基础设施通过端口注入应用层。跨域只能使用 `contracts`，禁止跨域 Repository、表写入或实体复用。`bootstrap` 负责装配；`shared` 仅存放少量通用技术代码，不收纳业务规则。出现循环调用时由上层用例编排，避免模块互相驱动。后续添加实际业务代码时增加 ArchUnit 等依赖边界检查。

## 平台能力

| 目录 | 职责和边界 |
| --- | --- |
| platform/identity | 企业认证、用户组织、RBAC 和数据范围；当前只有关闭业务入口的配置 |
| platform/jobs | 通用任务状态、租约、进度、重试、取消和结果引用；不保存各算法领域模型 |
| platform/workflow | 审批流程、参与者和操作记录；领域仍拥有方案发布规则 |
| platform/audit | 操作人与动作、前后版本、请求 ID；敏感数据脱敏 |
| platform/snapshots | 可重现的输入快照、内容校验、来源版本和有效时间 |
| platform/files | 文件元数据和存储端口，连接本地或企业文件服务 |

这些目录目前只预留结构。认证方式待企业环境确认；若使用同源会话，应继续保留 CSRF 防护并定义前端令牌交换，不通过关闭安全保护解决联调问题。

## 外部适配与持久化

`integration/algorithm` 放算法协议与 HTTP 客户端适配；其他目录分别对接 ERP、MES、WMS、TMS、质量和数据平台。外部 DTO 在适配层转换成 SCOS 模型，避免业务域直接依赖厂商 SDK、字段或状态码。连接凭据只存在服务端。

数据库目标为 MySQL 8，首次持久化实现时引入 Flyway 和数据访问依赖，按数据归属建立表。计划持久化任务、任务尝试、方案版本、快照、审批记录、审计和投递事件。目录中的迁移说明不是实际迁移脚本。

- 本地数据库事务围绕一个业务用例，网络调用不占用长事务。
- 方案更新使用预期版本校验；已发布方案保留不可变版本，调整产生新版本。
- 跨系统写入采用幂等键、投递状态、重试和补偿；不假设 HTTP 调用可以加入数据库事务。
- 业务变更和待投递事件使用同一事务写入，再由后台工作线程发送；重复消费必须可去重。
- 组织与数据权限从已验证身份推导，后端校验用户选择的组织上下文，不能信任客户端传来的组织 ID。

后端可先单实例部署，算法服务按计算资源单独部署。后台任务的持久化、租约和重复处理保证完成后才扩展多实例。数据库、HTTP 和文件服务需要各自的超时、容量上限和观测指标；不要使用无界线程池承接求解任务。
