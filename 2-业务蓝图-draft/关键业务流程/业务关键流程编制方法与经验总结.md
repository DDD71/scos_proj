# 业务关键流程编制方法与经验总结

## 1. 文档目的

本文档总结从标书、技术方案和现有蓝图样例中提炼业务关键流程的方法，用于指导后续各业务模块的蓝图编制。

业务蓝图不是技术实现设计，也不是将需求条款逐条画成流程。它需要用简洁、稳定的业务链路回答以下问题：

- 谁在什么条件下发起业务；
- 业务经过哪些关键判断、人工确认和责任交接；
- 系统生成什么业务结果；
- 结果由谁确认，并交给哪个环节继续执行；
- 异常时返回哪个环节，或转入哪个外部流程。

## 2. 编制前的输入资料

建议至少准备以下三类资料：

1. **标书或用户需求**：用于确定建设范围、必须覆盖的能力和系统边界。
2. **本模块技术方案**：用于理解数据来源、业务规则、系统交互和输出结果。
3. **已确认的蓝图样例**：用于统一章节结构、流程颗粒度、图形语言、配色和表格格式。

阅读时应把文档中的陈述分为四类：

| 类型 | 识别方法 | 在蓝图中的处理方式 |
|---|---|---|
| 业务活动 | 有明确执行者，并改变业务状态 | 候选流程节点 |
| 业务决策 | 需要人工确认、审批或选择分支 | 优先保留为关键节点 |
| 系统能力 | 数据获取、计算、校验、存储等 | 通常合并到业务节点的处理说明 |
| 业务规则 | 约束、阈值、判断标准和追溯要求 | 写入关联规则、处理说明或异常/分支 |

## 3. 业务关键流程的编制步骤

### 3.1 先确定模块边界

在画图之前，先用三张清单界定范围：

- **模块负责什么**：本模块必须完成的核心业务结果。
- **模块依赖什么**：上游计划、主数据、价格、订单状态等默认可获取的输入。
- **模块不负责什么**：由其他系统或业务部门承接的执行活动。

边界必须以标书和已确认需求为依据。不应因为某项能力在业务上“可能有用”，就默认系统具有该决策权。

### 3.2 提炼候选流程

候选流程应由业务闭环提炼，而不是由功能菜单拼接。一个可独立表达的关键流程通常具有：

- 清晰的触发条件；
- 相对独立的业务目标；
- 至少一次业务责任交接、判断或人工确认；
- 可明确命名的输出结果；
- 能说明流程何时结束。

如果一组步骤只是某个节点内部的数据处理，应合并到“处理说明”，不单独拆成流程。

### 3.3 判断是否应成为独立流程

可使用以下问题快速判断：

1. 它是否有不同于现有流程的触发方式？
2. 它是否产生可独立管理的业务结果？
3. 它是否包含新的责任角色、审批或业务状态变化？
4. 它是否是标书明确要求的业务闭环？
5. 把它合并到现有流程后，是否会使业务语义不清？

如果多数答案为“否”，则更适合作为现有流程的节点、分支或关联规则。

### 3.4 绘制骨干流程

先用文字写出最短业务链路：

> 触发 → 形成业务对象 → 系统分析或生成建议 → 业务人员评审 → 确认/审批 → 发布或交付 → 结束

这只是通用骨架，不是强制模板。节点数量应由业务完整性决定，不应为了“简洁”强行压缩，也不应将每个数据获取和内部计算都画成节点。

优先保留以下节点：

- 关键业务对象的形成或发布；
- 人与系统之间的责任切换；
- 部门或系统之间的业务交接；
- 影响流程走向的判断；
- 人工调整、确认或审批；
- 异常处理或返回修改；
- 有明确业务价值的输出结果。

### 3.5 设计泳道和执行角色

泳道用于表达责任边界，不是系统架构图。应遵循：

- 按参与方或执行角色设置泳道，如上游计划、采购人员、SCOS、外部执行系统；
- 参考样例从上到下排列泳道，业务流转也尽量自上而下；
- 节点放在真正承担责任的泳道中；
- 不要为了排版方便而改变业务责任；
- 其他系统只在发生关键业务交接时出现，不用展开其内部流程。

### 3.6 补充系统标识和业务单据

蓝图样例中的“PLM”类小标识，用于说明节点由哪个系统支撑，它不代表额外的流程步骤。在业务跨系统或需要明确系统责任时，可增加 SCOS、SAP、E采、TMS 等系统标识。

对业务中具有明确意义的输入或输出，可使用单据或文档图形，例如“月度采购方案”“供应商评价结果”和“资质/风险预警”。

添加前应确认：

- 该标识能帮助读者理解系统责任；
- 该单据是关键业务输入或输出；
- 不会因为图形增加而虚构新的业务范围。

### 3.7 为每个流程编制节点说明表

每一个流程图后应紧跟一张节点说明表，格式统一为：

| 节点编号 | 节点名称 | 执行角色 | 输入/输出 | 处理说明 | 异常/分支 | 关联规则 |
|---|---|---|---|---|---|---|
| 10 | 使用动宾结构命名 | 实际负责的角色或系统 | 写明业务对象及结果 | 说明关键逻辑和业务意义 | 说明 Y/N 走向、退回和异常处理 | 规则编号或制度依据 |

编写要求：

- **节点编号**：建议按 10、20、30 递增，便于后续插入节点；开始和结束可直接写“开始”“结束”。
- **节点名称**：应是业务动作，如“评审并调整采购方案”，避免只写“数据处理”。
- **执行角色**：区分业务人员、系统自动和外部系统，不使用含混的“用户”。
- **输入/输出**：使用业务语言，不必展开字段级数据结构。
- **处理说明**：解释“做什么、为什么、形成什么”，同时容纳不必在图中展开的系统计算。
- **异常/分支**：与图中的判断和连线一致，不要只写“提示错误”。
- **关联规则**：使用统一编码，并保证流程号、节点号可追溯。

### 3.8 校验业务闭环

图和表完成后，应逐节点检查：

- 每个节点是否有明确执行角色；
- 每个输出是否被后续节点使用；
- 每个判断是否有完整分支；
- 退回线是否回到可以解决问题的节点；
- 审批通过后是否产生可执行的业务结果；
- 外部流程是否只表达交接，没有越界展开；
- 图中的节点编号、名称和表格是否一致。

## 4. SVG 流程图的设计规范

### 4.1 布局

- 泳道从上到下排列，保持与蓝图样例一致。
- 主流程尽量向下推进，使读者按页面自然阅读方向理解流程。
- 相同泳道内的连续活动可水平排列，但不应把整张图做成从左到右的部门排列。
- 退回线和分支线尽量从图形外侧绕行，避免穿过节点或与主线交叉。
- 同一连线使用尽量少的转折点，箭头方向必须清晰。
- Y/N 标识放在对应分支出口附近，不要和节点文字重叠。

### 4.2 节点密度

不设置机械的节点上限。对每个候选节点询问：

- 删除它后，是否会丢失责任交接、业务决策或状态变化？
- 它是否只是默认可获取的数据或系统内部计算？
- 它能否合理地并入前后节点的处理说明？

第一个问题为“是”时应保留；后两个问题为“是”时通常应合并。

### 4.3 视觉风格

- 以黑、白、灰为主，使用一种主色表示系统标识或关键提示。
- 不用多种高饱和度颜色区分节点类型。
- 活动、判断、单据、开始/结束使用稳定一致的图形。
- 保持字号、边框、圆角、线宽和箭头样式统一。
- 节点文字优先使用简短业务用语，详细解释放在表格中。

### 4.4 技术校验

SVG 完成后至少进行以下检查：

- XML 可正常解析；
- Markdown 中的 SVG 相对路径真实存在；
- 图形无裁切、文字无溢出、箭头无遮挡；
- 连线不穿过不相关节点，尽量不交叉；
- 图中所有节点均在表格中有对应说明；
- 系统缩写、业务名称和编号与全文一致。

## 5. 业务边界的把握经验

### 5.1 不把“可用于决策”写成“系统代替决策”

系统可以生成建议、评分、风险提示和备选方案，但最终的供应商选择、数量调整、风险接受和业务发布通常需要业务人员确认。

流程中应清晰区分：

> 系统生成建议 → 人员评审和调整 → 审批/确认 → 系统发布

### 5.2 不因技术方案中的推演而扩大业务范围

对标书没有要求、业务也没有确认的能力，应避免使用过度具体的措辞。例如，如果采购系统不负责决定具体发货方式，应使用“到货安排”“发货与在途信息”等宽泛且准确的表述，不应把“分批发货决策”加入采购优化范围。

### 5.3 合理安排跨模块能力

一项能力应放在它的主要业务目标所属模块中。例如：

- 正常周期内生成采购建议，属于采购方案制定；
- 用户主动设置价格上涨、产能受限或供应中断等假设条件并比较多个情景，更适合归入供应链驾驶舱的沙盘模拟；
- 采购模块可为沙盘模拟提供方案、成本、供应能力和供应商风险等输入，并将模拟结论作为采购决策参考。

### 5.4 区分主流程、子流程和外部流程

- **主流程**：本模块负责的完整业务闭环。
- **子流程**：主流程中可复用、需单独说明的业务处理。
- **外部流程**：超出本模块范围，本图只表达发起、交接或接收结果。

当异常涉及质量、运输、合同或财务专业处理时，应写成“转相应外部业务流程处理并反馈结果”，不在采购蓝图内展开专业细节。

## 6. 常见问题及修正方法

| 常见问题 | 典型表现 | 修正方法 |
|---|---|---|
| 把功能列表当成业务流程 | 每个功能都是一个节点，看不出责任和闭环 | 重新围绕触发、决策、交接和结果组织流程 |
| 节点过多 | 数据获取、清洗、计算、排序都被单独画出 | 将默认可获取数据和内部算法合并到处理说明 |
| 节点过少 | 人工确认、审批和责任交接被省略 | 恢复影响业务状态和责任归属的节点 |
| 模块越界 | 采购系统直接替用户做最终决策，或展开运输、质量细节 | 将系统定位为建议和提示，通过外部交接表达其他模块 |
| 虚构需求 | 将“可能有用”的能力写成标准流程 | 回到标书和已确认需求，无依据时删除或使用宽泛表述 |
| 泳道方向不统一 | 样例为上下泳道，新图却按左右部门排列 | 按样例重构为自上而下的泳道布局 |
| 连线交叉 | 退回线穿过节点或与主线重叠 | 调整节点位置，将退回线放在外侧并减少折点 |
| 颜色过多 | 每类节点都用一种颜色 | 回归黑白灰和单一强调色，通过图形而非颜色表达语义 |
| 图表不一致 | 图中编号、名称或分支在表中找不到 | 按节点编号逐一核对图和表 |
| 文件分散 | Markdown 与 SVG 分布在多个目录 | 终版文档和所有引用资产集中到同一 assets 目录 |

## 7. 推荐的迭代方式

如果模块较复杂或业务理解尚未稳定，不建议一次性完成全部流程。可按以下方式迭代：

1. 选择最核心、边界最清晰的一个流程做确认稿。
2. 先确认业务梳理思路，再确认泳道布局、配色和表格格式。
3. 将确认稿的规则复用到其他流程。
4. 完成后再从标书角度检查覆盖性，而不是单纯按流程数量判断是否充分。
5. 只保留一份终版，删除过程版、重复图和失效引用。

## 8. 交付前验收清单

### 8.1 内容完整性

- [ ] 所有标书明确要求的核心业务能力均有归属。
- [ ] 每个流程都有明确的触发、目标、输出和结束条件。
- [ ] 系统建议、人工确认和审批责任没有混淆。
- [ ] 外部系统和外部流程的交接点清晰。
- [ ] 没有超出标书和已确认需求的业务能力。

### 8.2 图形质量

- [ ] 泳道按参考蓝图从上到下排列。
- [ ] 主链路清晰，分支和退回线易于辨识。
- [ ] 连线不穿过节点，不存在不必要的交叉。
- [ ] 配色克制，字体、图形和线条风格统一。
- [ ] 系统标识和单据图形有明确业务意义。
- [ ] SVG 可正常打开且无元素被裁切。

### 8.3 图表一致性

- [ ] 每个小节都由一张 SVG 和一张节点表组成。
- [ ] 节点编号、名称、执行角色和分支在图表中一致。
- [ ] 表格严格使用“节点编号、节点名称、执行角色、输入/输出、处理说明、异常/分支、关联规则”七列格式。
- [ ] 文档中的所有 SVG 引用都能正常解析。
- [ ] 正文、图中和表格中不存在已删除或未确认的业务表述。

### 8.4 文件交付

- [ ] 只保留一份终版主文档。
- [ ] 主文档与其引用的 SVG 集中存放在同一目录。
- [ ] 文件名称能够准确表达模块和流程名称。
- [ ] 不存在确认稿、临时稿、旧版 SVG 或无效相对路径。

## 9. 本次采购优化蓝图的关键经验

本次采购优化模块最终用四个关键流程表达主要业务闭环：

1. 月度采购方案制定；
2. 供应商评价与准入预警；
3. 采购计划滚动调整；
4. 采购执行跟踪。

形成的主要经验是：

- 流程数量不是判断蓝图是否完整的依据，应以标书覆盖、业务闭环和责任边界为准。
- 对于默认可获取的数据，不必将每个获取步骤画出；但人工评审、审批、状态变化和跨系统交接不能为了简化而省略。
- 情景假设、方案对比和风险模拟更适合归入驾驶舱沙盘模拟，不应因为需要采购数据就归入采购模块主流程。
- 供应商评价与准入预警具有独立触发、复核、状态调整和发布闭环，适合作为独立关键流程。
- 对标书未明确的业务细节，优先使用符合已知边界的宽泛表述，不为了让流程“看起来更完整”而虚构决策权。
- 先用一个核心流程确认业务思路和视觉规范，再批量完成其他流程，能有效减少全文重构。

## 10. 结论

一份合格的业务关键流程文档，应在“完整”与“简洁”之间取得平衡：

- 用足够的节点表达决策、责任、交接和状态变化；
- 将默认数据获取和内部技术处理收敛到节点说明；
- 用标书和需求控制范围，不替业务虚构新的系统决策；
- 用统一的泳道、图形、表格和编号让不同模块的蓝图可比较、可追溯；
- 最终让业务人员能够一眼看懂“业务如何运转”，让设计和开发人员明确“系统应支撑到哪里”。
